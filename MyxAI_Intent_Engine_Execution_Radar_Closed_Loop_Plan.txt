# 一、整体战略目标

## 1.1 为什么要做意图引擎 + 执行雷达闭环？

当前 MyxAI Desk 已具备：

* ✅ 执行能力（Nanobot 工具调用）
* ✅ 执行记录（exec_steps）
* ✅ 执行雷达统计（成功率 / 工具使用 / 有效步数）
* ❌ 缺少“决策侧记录”
* ❌ 缺少“学习机制”
* ❌ 缺少“可控的策略层”

换句话说：

> 现在你有“发动机 + 行车记录仪”，
> 但还没有“自动驾驶系统 + 驾驶决策分析仪”。

---

## 1.2 本次闭环升级的核心目标

我们要把系统升级为：

> 一个可学习、可解释、可控、可评估的端侧执行智能体系统。

闭环目标包括：

1. 提升执行效率（减少无效 tool call）
2. 提升执行准确率（减少误路由）
3. 降低 LLM 依赖度（复用成功计划）
4. 提供可解释性（为什么这么执行）
5. 提供持续优化能力（训练与评测闭环）

---

# 二、系统架构升级总览

## 2.1 当前架构（简化版）

```
User → LLM → Tool Calls → Executor → Radar统计
```

## 2.2 升级后架构

```
User
  ↓
Intent Engine
  ↓
(可选 Case 检索)
  ↓
仲裁器
  ↓
(复用计划 OR LLM 规划)
  ↓
Executor
  ↓
Validator + progress 标注
  ↓
Execution Radar
  ↓
Trainer / Eval / 策略调优
```

# PR-1：意图引擎最小骨架 + 工具裁剪

---

## 业务目标

### 目的

1. 建立“决策记录层”
2. 降低工具误用率
3. 减少 LLM 搜索空间
4. 建立后续闭环的基础数据

### 当前痛点

* LLM 每次面对全部工具
* 工具空间大 → 搜索成本高
* 无法统计“路由质量”

---

## 功能需求

1. 每个用户 turn 必须产生一条 Intent 记录
2. 记录路由预测结果
3. 根据预测裁剪 tool_defs
4. 可通过配置关闭该功能

---

## 技术实现

### 1. 新增 ie_runs 表

记录：

* 用户文本
* 上下文信息
* 路由结果
* 决策模式
* 最终 outcome

这一步建立“决策侧可观测性”。

---

### 2. app.py 接入点

在 `_patched_process_message()` 进入 tool 循环前：

```
1. 构建 context
2. 调用 intent_engine.predict()
3. 写 ie_runs
4. 裁剪 tool_defs
```

---

### 3. 工具裁剪策略

初版规则路由（不依赖模型）：

* 包含“打开/点击” → ui/browser
* 包含“下载/网页” → browser
* 包含“文件/目录” → fs
* 包含“git/命令” → shell

然后：

```
allowed_tools = route.tool_group
tool_defs = filter(tool_defs, allowed_tools)
```

---

## 验收指标

* ie_runs 有记录
* 平均 tool_defs 数量下降
* 执行成功率不下降

---

## 风险控制

* 提供 routing_enabled 开关
* 保留基础工具白名单

---

# PR-2：Case 检索外挂（先检索，不复用）

---

## 业务目标

### 目的

1. 让系统“记住历史经验”
2. 在不改变执行路径的前提下提高准确率
3. 降低 LLM 幻觉率

### 当前问题

* 每次任务都当新任务处理
* 无法利用成功轨迹
* 无法避免历史失败坑

---

## 功能需求

1. 存储成功/失败案例
2. 建立 HNSW 向量索引
3. 在低置信或失败时检索 topK
4. 将 pitfalls 注入 system prompt

---

## 技术实现

### 1. 新表 ie_cases

保存：

* task_text
* context_fp
* plan_json
* pitfalls
* fail_reason

---

### 2. HNSW index

存储位置：

```
~/.nanobot/models/intent_engine/hnsw.index
```

---

### 3. 仲裁逻辑（仅控制是否注入 hints）

```
if route.conf < T_route_low:
    attach hints
```

---

## 验收指标

* case 命中率 > 0
* 失败重复率下降
* LLM 生成计划更稳定

---

## 风险控制

* case_retrieval_enabled 开关
* hints 长度限制

---

# PR-3：PlanRunner（复用计划，跳过 LLM）

---

## 业务目标

### 目的

1. 实现数量级性能提升
2. 减少 LLM token 消耗
3. 提高稳定性

### 当前问题

* LLM 每次都重新规划
* 重复任务浪费算力

---

## 功能需求

1. 高相似度时直接执行历史 plan
2. 跳过 provider.chat
3. 仍记录 exec_steps
4. 仍支持安全闸

---

## 技术实现

### 新模块：plan_runner

执行流程：

```
for step in plan:
    invoke_tool(step)
    validate(step)
    write exec_steps
```

---

### 仲裁器升级

```
if sim > T_case_reuse and context_exact:
    decision = reuse_plan
```

---

## 验收指标

* llm_called=false 的任务比例上升
* 平均执行时间下降
* 成功率不下降

---

## 风险控制

* 高风险操作禁用复用
* 强制验证步骤

---

# PR-4：progress/validator + 有效步数修复

---

## 业务目标

### 目的

1. 修复有效步数模型
2. 真实衡量单/多任务
3. 为训练提供质量标签

### 当前问题

* effective_steps 统计失真
* 无法判断“是否推进状态”

---

## 功能需求

1. 每步执行后判断 progress
2. 写入 exec_steps.progress
3. 雷达按 progress 聚合

---

## 技术实现

### 1. exec_steps 表新增字段

```
progress INTEGER
state_sig TEXT
```

---

### 2. progress 判定规则（初版）

* URL 变化 → progress
* 文件新增/删除 → progress
* 命令 exit_code=0 且输出变化 → progress

---

### 3. 雷达聚合升级

```
effective_steps = sum(progress == 1)
```

兼容旧数据 fallback。

---

## 验收指标

* 单任务比例合理
* 多任务统计真实
* 重试循环能被识别

---
